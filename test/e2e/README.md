# Assistant page journey

`assistant-journey.mjs` drives the DevBoard assistant page (小川) on the real workbench with the verify skill: a fresh isolated run, the current source tree installed with `agh plugins add` and adopted on the Agents page, and the loopback provider fixture (`tools/acceptance/provider-fixture.ts`) as the model. The fixture answers with scripted DevBoard tool calls; every action under test is a click or typing.

It covers: the page opens and the session is created (listed as 小川, CLI agrees); a request becomes tool calls (project created, gate submitted and pre-checked) with collapsed progress lines, a reply and rail updates; an intervention answered inline and a person-decided gate approved in its card, each followed by the automatic hand-back; a TR1 gate (no customer rep) whose panel appears below the reply and is signed as 「技术负责人」 in the chat, and an ECR approval flow (five roles one at a time, then the CCB node) agreed in the chat, with no page or demo-role switch (steps c2b, c2c) (chat line plus a new model request carrying the hand-back text); a reload as second view (same session re-attached, decisions in the store, no second hand-back); a shell permission card that shows the whole command and runs after 允许一次; board writes raise no permission card, even in a turn tainted by shell output, while shell still does; a document written with `devboard_artifact_record` and `content` in a turn that already read the board raises no card and lands in the project directory of the isolated workspace, with its deliverable card shown; a role child (architect) writes docs/SAD.md with `devboard_doc_write` (whole content, then sectioned edits) in a turn tainted by an earlier spawn result and raises no card, its tool list holds only that one board tool, and a tainted child's host `write` still raises a card (step d4); rework by continuation: a second `subagent_spawn` after a spawn result raises a card whose reason is the taint, while `subagent_send_message` to the first developer child lets its host `edit` land with a card that does not carry the taint reason (step d5); reviewer and quality children spawned after a spawn result, as a review meeting does in a tainted turn, read the project and raise no card (step d6); the read-only 「看板操作免确认」 label; step h (`blocked-steps.mjs`): four identical board writes trip the repeat check and the turn ends `blocked`, the chat shows the explanation and 「继续」 (click starts a new turn, light/dark screenshots), a message typed after a blocked turn starts a new turn, and a role child finishing while the coordinator is idle (its first model request held 15 s by the proxy's `delayChild`) wakes the coordinator through the page.

Run (never against your own daemon; the helper uses a fresh `/tmp/agh-v-*` root):

```sh
AGNES_REPO=${AGNES_REPO:-$HOME/agnes-harness}
H=$AGNES_REPO/.claude/skills/verify/scripts/agh-verify.mjs
node $H build                      # reuses a matching runtime
node $H launch                     # prints RUN=<root>
node $H drive <this-repo>/test/e2e/assistant-journey.mjs --run <root>
node $H cleanup --run <root>       # always
```

Screenshots, ARIA snapshots, CLI transcripts and `result.json` land under `.agnes-tmp/verify/evidence/` of the open-source checkout. `AGNES_REPO` overrides the checkout path (default `~/agnes-harness`). The folder is not in the package `files`, so it never ships.

## Watch center journey

`watch-journey.mjs` drives 值守中心 with the loopback provider fixture as the group's coordinator: the sidebar entry below 小川, the 我是谁 picker, an empty group (no seeded activity), the rule layer stopping chatter without creating a coordinator session, and then a real coordinator session whose scripted tool calls (`devboard_watch_decide` / `_ticket` / `_reply`) accept an @研发协调员 request (ticket in the 子 Agent lanes), log progress after a thread reply, ask the technical lead (not in the project manager's list), and answer in the group after the lead's approval, which reaches the coordinator as a new model request; a second ticket finished by the coordinator (交付 +1); the coordinator's shell permission request shown for managers only with 允许一次 / 拒绝; a reload re-attaching the same session (CLI session list); rule and member permissions; light, dark and narrow screenshots; a plugin hot reload showing the CAPABILITY_DENIED notice and 重建协调员会话 (the old session stays listed); the signal desk and funnel drawer. Message ids (MSG-n / TH-n) are deterministic in a fresh run and used in the queued tool calls. The hot reload step is the same one the assistant journey has and can be flaky; rerun once. Run it like the assistant journey with `watch-journey.mjs` as the file.

Step o plays 「宁川的一天」 on the group after step n: the signal desk shows the number of events the rule layer would hand to the coordinator (computed from the server's rules, one real model call each) and needs a confirm click; cancelling posts nothing. At 16x it checks that pausing stops new events, that the position survives an identity switch, that filtered events show 已过滤, that the funnel deltas equal the plan (规则挡掉 and 交给协调员判断), that a coordinator-bound event reaches the fixture as a model request with the watch brief, a provenance chain opened from a funnel number, light/dark/narrow screenshots with the full day in the group, and the reset (disabled for a non-manager, empties messages, decisions and tickets for the technical lead while members and rule modes stay). The first-run step of the journey occasionally times out waiting for 「Add account」 on a fresh run; clean up and launch again.

## Reload history journey

`reload-history-journey.mjs` builds a long 小川 conversation (`RELOAD_ROUNDS` rounds of `RELOAD_TOOLS` read-only board calls, about 1000 ledger rows per round with the default 60 tools), reloads the page and expects the history back; then hot-reloads the plugin the way the dev sync does (changed package, install again, re-adopt) with the page left open and expects the history on the page without a reload (the host swaps the client modules in place), and again after a reload; then opens a second tab on the same session, reloads the first and expects the history again and a shell permission card on the page opened last. Run it like the assistant journey, e.g. `RELOAD_ROUNDS=3 node $H drive .../reload-history-journey.mjs --run <root>`. It creates no projects: hundreds of them make the board read fail with the plugin backend unavailable. It ends with an F5 on the URL-selected session (the workbench has read the session before the page mounts, so the history is rebuilt from the UI projection) and a new conversation + dev sync + F5. `RELOAD_WATCHED=1` installs into the watched `<home>/plugins/devboard` folder and syncs it the way `devboard-dev-sync.sh` does (the run then ends with two console 503s from the plugin restart window).

## Continue-after-collect repro

`continue-collected-journey.mjs` spawns a role with `wait: false`, lets the completion notice wake the coordinator, then runs `subagent_list`, `subagent_collect` and `subagent_send_message` (accepted); it then reloads the plugin and continues the same child again, which returns `E_CHILD_NOT_FOUND` although the child is still listed `idle continuable` (the record is `cancelled`). See the review-reject spec for the base code path. Run it like the assistant journey.

## Assistant demo journey

`assistant-demo-journey.mjs` drives 「小川演示」, the replay of one real 小川 run (data from `scripts/assistant-demo-export.mjs`, page in `client/demo/assistant-run-demo.js`). No model call is made; the fixture account only lets the first run and the adoption through. It checks the sidebar order (小川 → 小川演示 → 值守中心 → 值守中心 演示), play and pause (the clock stops), scrolling up during playback (the view stays put while lines keep arriving; scrolling back to the bottom resumes following), scrubbing to the end (six stages 已通过, more than 13 turns) and back, and a dark screenshot. Run it like the assistant journey with `assistant-demo-journey.mjs` as the file.

Regenerate the data from a later run: `node scripts/assistant-demo-export.mjs <events.json> client/demo/assistant-run.js` (input: JSON array of ledger rows).
